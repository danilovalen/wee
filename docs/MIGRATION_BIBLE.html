wee: moving to Godot

Register 464, 2026-10-25. The plan, built the way the chip game's was. Reasons and counts live in docs/GODOT_DIAGNOSIS.md.

1. The answer

Godot 4 fits wee better than it fitted the chip game, and the expensive half is already done. The rules are already pure and apart from the screen. Port once the rules stop moving; keep designing levels on the web until then.

The one real risk is speed: pressing Run searches the room. That gets measured in the first week.

Decided, 2026-10-25: every platform. Phone apps, PC with Steam and Deck, console through a porting house, and a web build. So touch, mouse, keyboard and controller are all first-class from the first build, and the layout has to hold both a phone and a TV.

Decided, 2026-10-25: the look is not chosen yet (pixel, SVG or voxel), and the UI grows from today's. So the board is drawn by one swappable skin that only reads the game state: a 2D skin and a 3D voxel skin must both be possible without touching the rules, and the slice uses a plain stand-in.

Decided, 2026-10-25: both orientations. The room stays centred and keeps its place; the palette and goal card sit beside it in landscape and below it in portrait. One layout with two arrangements, never two games.

2. How the chip game did it

  1. Measure first. Lines per part, how many times the rules touched the screen.
  2. Name what would change the answer. Its first answer was "stay on the web". You said audio, controller, console, and learning a real engine, so Godot moved to first.
  3. Split first, as the test harness. Rules in one module with no screen in it, the web game kept playable, then the Godot rules run beside it with the same seed and moves, and the two states compared.
  4. A one-week slice to learn on: one chip, one socket, one animation, controller, one sound.
  5. Decide the cheap things early: controller-first, landscape, 640x360 pixel art, GDScript.
  6. Your feature picks became hooks. Want or maybe scheduled nothing; both set what the code must allow.

What does not carry over: the chip game's screen is dense text, which the web is best at. wee is a grid of tiles and sliding pieces, which a game engine is best at.

3. What is here, and what happens to it

4. The one real risk: Run is a search

Run does not replay a stored answer. It searches the room (up to 20,000 positions, up to 2,000 shortest paths), replays each path and judges every goal. In the browser, every known room's check adds up to 0.8 seconds. GDScript runs that kind of loop many times slower than a browser does.

RouteCost
1. Typed GDScriptnone extra; often enough
2. Positions stored as bytes, not texta small rewrite of the visited list
3. The solver alone in C++ (GDExtension)a build per platform

Which one is a measurement, not a choice: the slice times the worst known room.

5. The route

  1. Freeze a rule set and tag it. Rules moved twice today; porting a moving target doubles every change.
  2. Record traces in JavaScript: every known room, every robot path, what the game reads at every tick. One Node script.
  3. The slice, one week: the solver timed, one room drawn, the robot sliding, Run's verdict, by touch and by controller.
  4. Port rules, then solver, then campaign, each checked against the traces.
  5. Rebuild the screens, editor first: building the room is the game.
  6. The web game stays playable the whole time. Levels keep being designed there.
